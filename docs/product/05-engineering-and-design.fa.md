# ۵. معماری، طراحی و قواعد توسعه

## پشتهٔ فعلی و نقش بسته‌ها

- Laravel 13 و PHP حداقل 8.3؛ Composer و Node حداقل 22 برای ابزارهای فعلی.
- Blade برای قالب، Livewire 4 برای تعامل سروری و Alpine همراه Livewire برای تعامل سبک مرورگر. Alpine را دوباره جدا راه‌اندازی نکنید.
- Tailwind 4 و CSS اختصاصی پنل، Vite برای ساخت، Lucide برای آیکن و فونت محلی `@fontsource/vazir`.
- Nwidart Laravel Modules برای بارگذاری ماژول‌ها و وضعیت نصب.
- Laravel Fortify برای ورود و خروج؛ ثبت‌نام عمومی کارکنان و ویژگی‌های اختیاری فعلاً خاموش‌اند.
- Spatie Permission برای نقش و مجوز، Activitylog برای زیرساخت رویداد، Media Library برای زیرساخت فایل.
- Morilog Jalali برای نمایش شمسی؛ ذخیرهٔ زمان UTC و نمایش در Asia/Tehran.
- Brick Money برای محاسبهٔ دقیق پول؛ مدل‌های مالی هنوز ساخته نشده‌اند.
- Chart.js نصب است، اما گزارش و نمودار فروش واقعی ساخته نشده است.
- PHPUnit، Pint و Prettier؛ GitHub Actions برای نصب، ساخت، بررسی و کش قالب/مسیر.

نسخهٔ دقیق بسته‌ها از lockfileها خوانده شود. کیف پول، اتصال تلفن، درگاه، پیامک و اشتراک هنوز نصب/فعال نیستند. بستهٔ جدید فقط با نیاز مشخص، سازگاری، مجوز مناسب و وضعیت نگهداری قابل قبول انتخاب شود. قالب پولی Vuexy/Metronic خریداری یا کپی نشده است.

## مسیرهای مهم کد

- `Modules/{Name}/`: مالک قابلیت، مسیرها، migration، مدل‌ها، Actions، Contracts و قالب‌های همان ماژول.
- `config/vira.php`: تعریف و وابستگی ماژول‌ها و پرچم‌های فعال‌سازی.
- `modules_statuses.json`: وضعیت فعال‌سازی Nwidart برای کل نصب.
- `app/Support/ModuleAccess.php`: بررسی فعال بودن، وابستگی و رد چرخهٔ وابستگی.
- `app/Support/ModuleServiceProvider.php`: بارگذاری مسیر، migration و view ماژول.
- `app/Http/Middleware/RequireModule.php`: کنترل فعال بودن ماژول سمت سرور.
- `app/Livewire/FoundationDashboard.php`: داشبورد آغازین، نه گزارش فروش کامل.
- `resources/views/components/layouts/`: قالب پایه و پنل؛ `resources/css/app.css` و `resources/js/app.js`: ظاهر و تعامل‌های مشترک.
- `database/seeders/DatabaseSeeder.php`: مجوزها و نقش‌های اولیه؛ حساب ثابت ایجاد نمی‌کند.
- `app/Console/Commands/CreateOwner.php`: ساخت مدیر بدون ثبت‌نام عمومی.
- `tests/Feature/`: آزمون‌های هسته، دسترسی و ساخت مدیر.

## قواعد مرزبندی

یک عملیات کسب‌وکار در یک Action روشن قرار گیرد. کنترلر و Livewire آن را هماهنگ کنند؛ قواعد موجودی و قیمت در قالب و جاوااسکریپت پراکنده نشوند. ماژول‌ها کنترلر یکدیگر را صدا نزنند. انتزاع، Repository و لایهٔ اضافه فقط در صورت نیاز واقعی اضافه شوند.

وابستگی فعلی: Catalog به Core؛ Inventory به Catalog؛ Customers به Core؛ Crm به Customers؛ Sales به Inventory و Customers؛ Pos و Storefront به Sales. Core الزامی است. CRM برای خرید اختیاری است.

نام ماژول در تنظیمات، namespace، مسیر و آزمون یکدست باشد. «غیرفعال بودن در نصب»، «خریداری شدن قابلیت برای مجموعه در آینده» و «مجوز کاربر» سه موضوع جدا هستند؛ فعلاً فقط اولی و سومی پایه‌گذاری شده‌اند.

## داده و امنیت

- کلید خارجی، یکتایی، محدودیت و ایندکس بر اساس فرایند واقعی تعریف شود.
- پول با واحد صریح و محاسبات دقیق؛ پیشنهاد فعلی ذخیرهٔ صحیح ریال و نمایش تومان است، اما پیش از schema فروش تصویب نهایی شود. float برای مبلغ مالی استفاده نشود.
- تغییرات مرتبط با موجودی و پرداخت در تراکنش و با مدیریت هم‌زمانی انجام شوند.
- درخواست‌های تکراری، callback و retry صف باید اثر تکراری نسازند.
- روی همهٔ ورودی‌ها اعتبارسنجی و روی خواندن/نوشتن کنترل مجوز انجام شود؛ در Actionهای Livewire هم بررسی لازم است.
- کارکنان و خریداران سایت دسترسی جدا دارند، حتی اگر بعداً از مدل یا guard مشترک استفاده کنند.
- اطلاعات خصوصی، فایل مکالمه، آدرس و فاکتور دیگران از API، URL، فایل عمومی یا خروجی قابل افشا نباشند.
- کلیدها، توکن‌ها، رمز اولیه، دیتابیس و دادهٔ مشتری وارد گیت و سند انتقال نشوند.
- برای تخفیف، تغییر موجودی، ابطال، خروجی و تغییر دسترسی، سابقهٔ قابل پیگیری در نظر گرفته شود.

## پایداری

خطای یک درخواست معمولاً همان درخواست را خراب می‌کند، اما خطای راه‌اندازی، دیتابیس مشترک و کمبود منابع می‌توانند کل برنامه را مختل کنند. معماری فعلی جداسازی کامل خرابی را تضمین نمی‌کند.

پیامک، پردازش صوت، خروجی سنگین و گزارش در صف با retry و timeout اجرا شوند. صف‌های پیشنهادی critical/default/notifications/reports هستند؛ دستور توسعه فعلی reports را پردازش نمی‌کند. در استقرار واقعی، worker گزارش با منابع جدا لازم است. رویدادهای جانبی پس از commit منتشر شوند. خرابی اطلاع‌رسانی نباید فروش را باطل کند؛ خطای موجودی/پرداخت نباید پنهان شود.

## طراحی پنل مورد تأیید

سایدبار سرمه‌ای، جمع‌شونده و گروه‌بندی‌شده؛ فضای محتوای خنثی؛ رنگ تأکیدی بنفش با گزینه‌های آبی و رز؛ حالت روشن و تیره؛ تایپوگرافی وزیر؛ کارت و جدول جمع‌وجور؛ آیکن‌های منسجم و تب‌های واضح. حالت موبایل با منوی بازشونده و چیدمان ستونی کار کند.

هاور باید بازخورد ظریف بدهد و انیمیشن کوتاه و قابل حذف با reduced-motion باشد. اطلاعات فقط با رنگ منتقل نشوند. کنتراست در تمام تم‌ها، focus کیبورد، نام کنترل‌ها و اندازهٔ لمس بررسی شود. ظاهر پنل مبناست؛ طراحی سایت هنوز به نمونه و تصویب جداگانه نیاز دارد.

## اجرای محلی

از ریشهٔ پروژه `composer dev` اجرا می‌شود: سرور روی `127.0.0.1:8017`، worker و Vite. URL پنل `/panel` و ورود `/login` است. سرور اجراشده در چت قبلی ممکن است امروز فعال نباشد؛ قبل از ادعای دسترسی زنده، آن را بررسی کنید.

برای XAMPP/Laragon، DocumentRoot باید `public/` باشد؛ تنظیم عمومی Apache و hosts در تحویل پایه تغییر نکرده است. PHP ترمینال از Laragon بوده، ولی Apache موجود متعلق به XAMPP است؛ نسخه و افزونه‌های PHP وب و CLI را یکسان فرض نکنید. راهنمای `docs/local-development.md` جزئیات بیشتری دارد.

SQLite برای نصب محلی آغازین استفاده شده است. تغییر `.env` به MySQL، انتقال خودکار داده نیست. migrations و سناریوهای هم‌زمانی خرید باید روی موتور دیتابیس مقصد هم بررسی شوند.

## تعریف انجام‌شدن هر مرحله

رفتار و معیار پذیرش مشخص، migration قابل بررسی، اعتبارسنجی، مجوز، آزمون موفق و بررسی مرورگر در صورت تغییر رابط. `composer check` و `npm run build` ابزارهای فعلی‌اند. بعد از تغییر رفتار، آزمون متناسب اجرا شود؛ تغییر صرفاً مستندات نیازمند اجرای همهٔ آزمون‌های نرم‌افزار نیست.

آزمون‌های فعلی از SQLite حافظه‌ای استفاده می‌کنند. هرگز `migrate:fresh` یا آزمون مخرب را روی دیتابیس کاری اجرا نکنید. هنوز تضمین کارایی و آمادگی تولید برای حجم مشخص تعریف نشده است؛ باید با حجم و میزبانی واقعی ارزیابی شود.
